## 结论

普通文件目录的删除、管理副本保留、撤销以及四端普通项目 MCP 条目移除流程通过隔离验证。功能尚不完善，至少有以下问题。

### 1. 删除共享目录时遗漏经链接使用它的 Agent（较高影响，已复现）

构造 `.agents/skills/demo` 实际目录和 `.claude/skills/demo` 符号链接。删除实际目录的预览只列出 codex、cursor，没有列出 Claude。根因是 `remove_resource` 使用单个扫描资源的 `r.agents`，没有汇总其他入口指向同一 canonical 目录的消费者。

影响：用户无法从确认提示完整判断影响范围；确认删除实际目录会让其他入口的链接失效。建议删除前汇总扫描到的真实目录、链接和嵌套资源，逐项展示受影响入口及 Agent，并区分已扫描与未覆盖范围。

### 2. 导入后原来源改变，管理关联丢失（中等影响，已复现）

按 `import_skill` 的字段格式建立一个已导入管理副本，确认扫描关联存在；修改原目录 SKILL.md，再扫描，`library_id` 变成 None。

`scan` 仅通过 installations 映射或内容指纹匹配管理版本；导入并不登记原来源为安装映射。因此来源改变后前端 `currentSkill` 为空，又展示导入按钮。后端的来源 ID 没变，会拒绝重复导入并提示使用检查更新。用户在当前抽屉中失去正确操作入口。

建议将“来源关联”“部署关联”“内容相同”分开记录和展示，内容变化不能抹掉来源关联；此时应提供查看管理副本或检查来源更新。

注意：此复现验证扫描/关联链路，管理记录依照导入逻辑构造；没有驱动真实窗口完整执行 import_skill 和原生确认对话框。

### 3. 链接入口显示删除按钮，但操作必然被拒绝（中等体验问题，已复现）

前端不依据 is_link 收敛移除按钮。后端 ensure_no_symlink_ancestors 会拦截链接目录，原始目录与链接均保留。

当前安全拦截正确；界面承诺与能力不一致。建议显示“移除此链接”并单独实现仅 unlink 的备份/恢复协议，或明确禁用并说明当前只支持真实目录，不能让用户靠点击报错了解限制。

### 4. 删除说明没有根据实际副本情况变化（静态代码确认）

所有普通 Skill 的移除预览都写“Agent Hub 管理的副本仍保留”，即使资源从未导入、没有管理副本。它并不检查 library_id 或副本是否存在。虽有操作前备份，这不等于已经存在独立管理版本。

建议有副本时显示实际管理副本；无副本时明确没有管理版本，并解释备份/撤销能力。按钮文案也应区分删除 Skill 目录与删除 MCP 条目。

## 已验证的正常流程

- 删除预览不立即删除普通 Skill 目录。
- 应用后普通 Skill 安装目录删除，已有管理副本与管理记录保留。
- 对删除计划调用真实 preview_undo 并应用，可恢复文件、空目录和 installations 记录。
- 符号链接入口移除被拒绝，链接与真实源均不删除。
- Claude / Codex / Cursor / Antigravity 普通项目 MCP 删除只移除目标服务，保留其他服务与根字段；撤销后配置恢复为原始字节。
- 原有 17 项检查全部通过，包含预览后外部变更拦截、权限范围、备份、路径/链接拒绝和配置值遮蔽等。
